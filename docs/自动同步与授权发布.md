# 自动同步、测试与授权发布

`main` 是你的定制版本；美国策略保存在 `policy/us-only.js` 和生成脚本中。上游 main 作为更新来源，不能再点击 GitHub 的 Sync fork 把整份上游合并进定制 main，也不保留原来无测试直接同步的定时任务。

每天北京时间约 08:20，GitHub Actions 执行：

1. 校验当前 main 的来源、生成一致性和测试。
2. 获取 cmliu/edgetunnel/main 的明确提交，仅导入原始 worker；保留你的配置、工作流和美国策略。
3. 应用策略；运行语法、17 项代理/认证/订阅测试，以及 11 项生成、发布编号、审批配置和上线检查测试。
4. 全部通过后创建候选提交，一次原子推送到 `upstream-candidate` 和 `main`，不强制推送。main 被别人同时改过、补丁不兼容、许可证变化或测试失败时停止，原 main 不变。
5. 自动触发发布准备工作流，按确定的 main 提交生成上传包、来源记录和 SHA256。普通测试与打包不读取 Cloudflare 密钥。

GitHub 计划任务可能延后。没有上游更新时不会产生新提交。机器人推送不会自动触发一般 push 工作流，所以同步任务通过 workflow_dispatch 显式触发发布准备。

## 你如何测试

GitHub → Actions → **Naiops CI**：每次 PR 或你自己推送 main 都运行测试，也可以点 Run workflow 手动运行。

Actions → **Sync upstream into custom main** → Run workflow：立即同步并测试。失败时看失败步骤；候选 patch 会作为运行附件保存 7 天，便于排查。不能忽略失败后强行推进 main。

本地在仓库执行：

```sh
bash scripts/verify.sh
```

修改定制逻辑时改 `policy/us-only.js` 或 `scripts/apply-us-policy.py`，然后重新生成 `_worker.js` 并测试。不要只改生成文件，否则一致性检查会拒绝它。

```sh
python3 scripts/apply-us-policy.py upstream/_worker.js _worker.js
bash scripts/verify.sh
```

## Cloudflare 如何要求你的授权

保护环境为 `cloudflare-production`：审核人是 `duiniwukenaihe`，仅 main 可部署，禁止管理员跳过审核，允许你批准自己启动的运行。发布 job 只有审核通过后才能获得这个环境的密钥；脚本还会再次检查审批规则，缺失时停止。

发布开关 `CLOUDFLARE_DEPLOY_ENABLED` 默认 `false`。2026-10-09，用户明确授权创建新项目、部署节点、设置密码并迁移域名；新项目 `naiops-us-github` 已发布测试通过的节点版本，`us.naiops.ccwu.cc` 已指向新项目。原项目 `naiops-us` 的 8000119 原因仍未由平台说明，旧项目保留，Git 原生自动构建已暂停。后续工作流发布目标为新项目，仍需用户审核；GitHub 环境发布密钥尚需由用户一次性配置。

要启用 GitHub 后续发布，一次性设置：

1. 仓库 Settings → Environments → cloudflare-production → Environment secrets → 添加 `CLOUDFLARE_API_TOKEN`。值由你填写，不发到聊天。按 Cloudflare 官方说明给目标账户的 Pages 编辑权限；当前 HOST、KV、ADMIN 保留在新项目设置中，工作流不修改它们。
2. Settings → Secrets and variables → Actions → Variables，将仓库变量 `CLOUDFLARE_DEPLOY_ENABLED` 改为 `true`。这个开关只允许排队，每次真实发布仍要求你的审核。
3. Actions → **Release after owner approval** → Run workflow，选择 main。revision 可留空使用该次运行的 main 提交；也可填写曾经进入 main 的完整 40 位提交编号。
4. prepare 通过后可下载 `naiops-release-提交编号` 附件，包含部署 ZIP 和 release-manifest.json。检查编号后，点击 **Review deployments**，选择 cloudflare-production，再点 **Approve and deploy**。只有这一步是每次发布授权。
5. 发布使用固定 Wrangler 4.147.0 和项目 naiops-us-github。新版本 `/healthz` 必须返回相同提交编号；不匹配就报告失败，不自动改指向其他版本。检查客户端使用明确的名称，避免默认 Python 客户端被 1010 拒绝而误报部署失败。

在等待期间 main 有新提交，不会改变当前待批准的包。如果待批准版本已经过时，应拒绝/取消那次运行，再启动新版本。发布串行执行，不自动批准或替你重试；GitHub 并发规则可能用新任务替代尚未开始的排队任务。

关闭发布开关会继续允许同步、测试和打包；取消不需要的待审核运行后，可以暂停所有实际发布。

## 自动验证能证明什么

本地与 CI 证明策略、认证边界、候选顺序、全部失败断开、订阅和包版本逻辑。上线健康接口证明绑定存在和版本匹配。

2026-10-09，经自定义域名的真实 VLESS 和 SS 加密连接均访问检测页成功，TLS 校验通过，出口为 3.132.174.45，国家为 US。原 Google 健康检查地址在真实链路中 TLS 握手失败，故障切换检测改为实测可达的 `https://www.cloudflare.com/cdn-cgi/trace`，要求 HTTP 200，每 300 秒检查。Mihomo fallback 的[官方说明](https://wiki.metacubex.one/en/config/proxy-groups/fallback/)为按顺序选择首个可用节点。

这些不证明免费候选的最终出口永久在美国、共享 IP 能长期登录 ChatGPT，或真实客户端能故障切换。主失败/全失败目前通过模拟回归验证；真实出口故障和客户端切换仍需单独验收，实际 ChatGPT 登录由你完成。
